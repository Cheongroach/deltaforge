# DeltaForge 小周报：主流框架迁移第 1 轮

记录开始：2026-10-25 14:07 +08:00，阅读整理于 2026-10-26。本轮想把独立 GDN 算子接入真实模型，先统一计算接口，再验证数值、更新参数和测完整训练步。

最终，相对 torch 参照的固定 H20 LoRA 子范围通过，原生默认／FLA 梯度分歧尚未定位。过程中的主要困难是版本与资产一致性、真实输入的浮点抵消，以及编译缓存对测量的影响。下面按任务说明如何处理，时间表放在后面供回查。

文中的 M1 是“共同契约与基线”，M2 是“完整单卡训练”；门禁是预先固定的数值阈值；payload 是远程任务携带的自包含源码与依赖；hash 是文件内容指纹。日志记录可复核的动作与决策依据，不把当时的计划写成最终结果。

## 小任务记录

### T01：版本与资产准备

**已做：** 核验当前环境，读取原生 Qwen3.5 模型实现，找到公开预训练模型资产和既有加载路径。

**问题与难处：** 之前的调研读的是移动的 Transformers main，其 kernel 接口与本地 5.2.0 不完全相同。worker 不共享开发机 `/tmp` 和用户目录，不能把本地存在的权重当成远程可用。

**候选：**

| 候选 | 优点 | 代价／风险 | 当前选择 |
|---|---|---|---|
| 直接使用最新 main | 新接口与后端入口较完整 | 版本漂移，改变多个变量，可能影响权重加载 | 不作为首轮默认 |
| 固定已有 5.2.0，再选择匹配的 FLA | 复用可核验的模型类与运行经验 | 需额外核对 FLA API／依赖 | 首轮方向 |
| 把已有资产路径直接写给 worker | 少写下载逻辑 | worker 不共享这些路径，无法复现 | 不采用 |
| 按来源／hash 在 worker 下载或从共享资产复制 | 自包含，可验证 | 首次传输与存储成本 | 后续核验后选择 |

**当时结论边界（14:13）：** 只有环境与源码核验，尚无新 GPU 数值或训练结果；后续终态见本文末尾。

**新增问题与解决：** GitHub API 限流，WikiText 下载网络不可达。改用已固定版本、许可为 Apache-2.0 的公开 ESCI 数据，并重新验证源 split hash。混合源数据包含没有 `task` 字段的模拟记录，准备脚本显式筛选 `esci_classification`；JSONL 商品文字还包含 Unicode 行分隔符，使用 LF 作为真实记录边界。保留失败，不把模拟样本混入本次训练。

**新比选：** 使用锁定 PyPI wheel＋SHA256 代替移动 main commit。首轮选择 FLA 0.4.1 是接口／已知环境匹配选择，不宣称它是 2026 年最新版强度；后续升级基线须重做全部门禁。

### T02：接口接入设计

**已做：** 确认 GDN callable 与普通 attention 配置是独立入口。原模型参数、卷积、norm 与投影继续由框架管理。

**问题与难处：** normalization 的位置／epsilon、query scale、state 布局、GQA 顺序都需要对齐。无梯度的 decode kernel 不可作为训练 backward。

**候选与决策摘要：** 首轮使用可恢复的层级 adapter；不对整个 Python 模块进行全局替换，不改预训练模型结构。先采用可微 PyTorch 组合路径做对照；编译路径与成熟 FLA 后端分别接受梯度门禁。是否增加解析 VJP，由保存激活与完整步实测决定。

**已实现：** `GDNBackend` 提供 torch、DeltaForge、compiled、FLA 与 recurrent 路径；层级 context manager 恢复原 callable。普通张量运算保存 autograd；FP16/BF16/FP32 用 FP32 累积，double 路径保留 double 以接受有限差分。packed／未知 gate transform 选项明确拒绝。CUDA FLA 不作为 NPU 回退。

**难处与处理：** BF16 normalization 的 arithmetic 会影响公平性。adapter 内使用 Transformers 5.2 fallback 的 epsilon 和输入 dtype 算术，FLA 对照关闭其内部重复 normalization；另保留真正原生默认 callable 的完整模型对照，区分适配器比较和框架原生比较。

### T03：数学与框架门禁

**已做：** 新增 double gradcheck、state 布局、跨 segment 梯度、scale、输出 state 选项、unsupported、真实 Qwen GDN 层输出／全部参数梯度、context 异常恢复和 checkpoint 验证。与原 8 项测试共同运行的 13 项断言已通过，结构化记录在 `training-results/cpu-gates.json`。

**问题与难处：** 工具沙箱会限制线程访问 `/proc/.../comm`；一次 5 项测试命令正常 exit 0，而 13 项命令在写出成功记录后仍被工具判为受限。限制 compiler 并发为 1 后仍复现，因此尚未证明是哪一类线程触发。断言通过与进程退出分别记录；worker 将在安装 FLA 前独立复跑。

### T05：真实模型训练准备

**方案：** Qwen3.5-2B 原生 text-only 模型，BF16、SDPA、相同卷积路径；LoRA rank 8，包含 attention／MLP／GDN 投影。每次 10 更新（2 warmup＋8 测量），两次独立进程；第二次反转后端顺序。模型加载要求 missing／unexpected／mismatched/error 全空；保存 logits、全部 trainable 参数梯度、loss、有效 token、完整 step 时间、峰值显存和验证 loss。

**比选：** 全参数训练更完整但成本与 optimizer 状态更高；本轮先闭合 LoRA 的完整 forward→loss→backward→optimizer，明确不把结果外推到全参数训练。动态长度会引入编译次数变量，首轮采用 256-token bucket，padding 不计入 loss／有效 token。验证 loss 仅是后端一致性证据，16 条数据不足以证明通用或业务质量。

**平台问题与比选：** 平台 create 请求限制 1 MiB，dryrun 和预检没有阻止超限。Base85 本地更小，但服务端 JSON 对 `<`／`>`／`&` 做 HTML escaping，实际请求反而增大。恢复 Base64，仅携带验证／worker 必需的 9 个 Python 文件，既保留源码 hash 自检，也低于请求限制；第三次成功创建。另一候选为先上传 HDFS/TOS 再传路径，本轮无需新增资产上传。

### T06：安装与归档准备

**已做：** 添加 0.3.0 的 pyproject、可选 Qwen/FLA 依赖、内部缓存忽略规则、训练接入说明。wheel 构建成功，直接从 wheel zip 导入并执行一次 CPU GDN，进程正常 exit 0。

**难处与处理：** `platform.py` 在 flat workspace 根目录会被 pip／setuptools 当成 Python 标准库 platform 导入，产生循环 import。更名为 `merlin_platform.py`，修改内部 launcher import；历史 snapshots 不改写，保持原始证据。公开 main 延续 `deltaforge/` 包目录形式，并省略绑定内部资源的 helper。

**第一轮终态：** worker 正常完成独立 CPU 回归（13 项，2.807s），模型／依赖 hash 均通过。默认路径与 torch 的全模型梯度误差越过预设阈值，因此停止后续训练，没有修改阈值。失败及 CPU 终态保存在 `training-results/attempt-01/`；normalization 与低精度算术是待验证假设，尚未定位根因。下一轮将分别保存各后端门禁与逐层误差，使一个失败不掩盖其余候选证据。

### T03／T05：第二轮诊断与有条件训练

**已做：** 门禁逐后端落盘，记录最大参数梯度误差贡献者；一个数值失败不再遮蔽其余候选。worker 只为通过同一门禁的后端安排训练，各子进程保留返回码与耗时，失败后继续归档独立结果。

**难处与处理：** 整模型比较混合局部 kernel 差异与前层误差传播。诊断截取 torch 参考模型首／中／末 GDN 的真实 Q/K/V/g/beta，同时固定对应上游梯度，再换核比较局部 forward/backward。对照 chunk32／64、共同 BF16 normalization、FP32 normalization 和 FLA normalization。

**比选与决策：** 不调整 8% 梯度阈值；失败后端不进入训练验收。未用的 FLA models/layers wheel 移出 payload，必需 GDN／normalization 均在锁定的 fla-core 0.4.1 内。lock 保存排除 wheel 来源和原因，第一轮资产记录不改写。资源 API 的查询名称为 NVIDIA-H20，与启动枚举 NVIDIA_H20 不同；按实际响应重新查询，未据空查询误判资源耗尽。

**预检记录：** 当前 create schema 校验与 dryrun 成功；最终 payload 直接用于 check-items，data.status=success，无业务 warn/hint，保留式合并 request_context.precheck_sid 后在 30 分钟有效期内提交。新任务使用同一镜像、资源组和队列；内部 receipt／原始日志放私有目录，公开报告只保留数值与源码 hash。

### T03：实际模型暴露幂零展开的稳定性问题

**第二轮终态：** 97 条结构化事件与证据归档已收集，worker 完整结束。torch 两个独立进程各完成 10 个真实 LoRA 更新，8,409,600 个可训练参数确实变化；validation loss 从 3.49007 到 2.33045，两次最终 adapter hash 相同。其余后端未通过整模型门禁，未安排训练；这不是 DeltaForge 的训练成果，也不是业务质量结论。

**问题与难处：** 原 `I-L+L²-…` 在实数域是有限、精确的幂零展开，但中间矩阵幂会出现大数抵消。随机 Q/K 的测试没有覆盖训练后近共线 key 与弱 decay，真实层出现巨大 forward 误差；compiled 也失败，编译没有解决算法稳定性。

**已复现的证据：** FP32 的严格下三角矩阵 L=0.999×tril(ones,-1)，C=32 时原展开 inverse max abs 32、relative L2 4.57553、方程 residual max 21.6954；分块逆 max abs 5.9605e-8、relative L2 1.4028e-8。C=64 时原展开最大误差 2.57698e10，而 block 最大误差仍为 5.9605e-8。共线 key、g=-1e-6、beta=0.999 的完整 GDN，原展开输出 relative L2 6.39724，block 1.9551e-7（对独立逐 token recurrence）。这是已复现的算法反例；与真实模型故障的因果对应仍等待第三轮固定输入对照。

**比选与实现：** 原幂零展开保留为 `inverse_method="doubling"` 的实验对照。新默认采用分块三角替代：块逆公式构造下三角 cross block，避免形成大矩阵幂；保留可微 PyTorch matmul。直接 `torch.linalg.solve_triangular` 作为独立候选／oracle，但跨厂商编译覆盖及性能不能默认成立。新增共线 key＋弱 decay 的 forward/backward regression，14 项 CPU 断言通过。本地使用已提供的 sandbox-exit 显式跳过受限 interpreter teardown；worker 将以正常退出再次复核。

**FLA 结论边界：** 固定上游梯度的首／中／末层诊断显示 FLA g/beta 梯度误差明显高于仅切换 FP32／FLA normalization 的误差；因此不能把整模型约 18% 的差异全部归因为 normalization。当前只确认锁定版本、输入与精度下不通过本项目门禁，不声称 FLA 普遍不正确。

**第三轮提交时的未解决项：** 原 `compiler.py` 的 semantic solve lowering 仍使用旧幂零展开，尚不纳入新训练后端支持承诺；训练 `compiled` 路径直接 compile 新 GDN。旧算子性能报告与快照保留，不能把它们作为新算法性能。第三轮重复使用同一 H20 配置与阈值，schema／dryrun／预检成功，无业务告警，已提交；等待终态后判断 M1/M2。

### T03／T05：第三轮稳定求解与真实 LoRA 闭合

**终态与证据：** 15:20 worker 完成，15:30 收集验证后平台为 done、pod exit 0。14 项 CPU 回归正常结束；固定真实层的新 block 输出误差为 1.97e-6／2.76e-5／3.34e-5，旧 doubling 为 3.49／4.14e-5／16.55。DeltaForge／compiled 整模型 logits 误差为 2.201%／2.235%，全部参数聚合梯度误差 2.724%／2.687%，均通过原阈值。

**已完成：** torch、DeltaForge、compiled 各两个独立进程、十个 LoRA 更新，共六个成功训练臂。所有臂 8,409,600 个 trainable 参数均有梯度，参数 hash 变化，同后端两次 final hash 一致。每次八个测量步有 1552 个有效预测 token；validation loss 降到约 2.33，与 torch 最大 abs 0.001605。复核脚本 `tools/report_training.py` 检查终态、预算、初始化／更新／同轮重复、数据 hash 和预设门禁。

**难处与解决：** 小的局部浮点误差会经整模型放大，不能要求 BF16 全部元素精确相等；按事先固定的聚合阈值记录原始误差。跨轮 torch 的最终 hash 和相对基线差异变化，同轮两个进程一致；没有追认跨作业位级确定性。四条 validation 只证明兼容性，不能证明泛化。

**边界与下一步：** native default／FLA 参数梯度误差仍为 21.89%／22.40%，被跳过训练。M2 相对显式 torch oracle 的固定 LoRA 子范围闭合；原计划的默认框架训练比较仍未闭合，M2 总体部分完成。下一轮优先定位默认／FLA backward，先在同一真实输入和上游梯度下比 BF16／FP32／double oracle，再核验版本／kernel backward；不提高阈值，不凭短训练 loss 相近推断梯度合格。

### T04：强基线性能与编译成本

**已完成：** 两次进程均保存 T=256／2048、16 heads、K=V=128 的 forward、backward、首次执行、saved tensor 和数值误差。准备／normalization／拷贝包含在调用中，hooks 只用于另外的保存量采集。

**实测：** compiled 完整训练 step 中位数 380.44／406.48ms，torch 837.78／822.58ms，同重复比为 2.02–2.20×。torch 第一次出现 2539.62ms 长尾，tokens/s 比值波动较大；本轮只记录观测范围。整模型 allocated 峰值约 4.516GiB，没有节省显存证据。随机算子 FLA 明显更快：T=2048 的 FLA forward／backward 约 0.68／1.23–1.31ms，compiled 约 9.48–11.98／13.78–15.67ms。

**难处：** 首次成本含 dispatch、编译、运行；前面 gate 和 validation 已可能预热磁盘 cache。compiled T=2048 在首 kernel 进程首次耗时 105.99s，第二进程 3.11s，不能当作完全独立冷启动比较。八步稳态样本也不足以给稳定 P95 或生产 SLA。

**比选与决定：** CUDA 通用加速应优先复用成熟 FLA；DeltaForge 本轮价值为可微、可直接编译的稳定 PyTorch 组合路径，尚无胜过 FLA 的证据。不采用随机 microbenchmark 合格就跳过真实模型 gate 的方案。M3 再比较直接 triangular／block／成熟核、明确冷缓存与重算策略，按完整步和成本选择；不根据当前速度硬编码全 shape 最优后端。
